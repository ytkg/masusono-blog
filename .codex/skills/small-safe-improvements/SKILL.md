# Small Safe Improvements

このプロジェクトのコードを読み、小さく安全な改善を積み重ねる。1回の実行で扱う実装は1件、対応する Issue と PR はそれぞれ1件とする。PR はマージせず、ユーザーが判断できる根拠を残す。

## 候補の選定

- リポジトリの AGENTS.md と、変更箇所に適用される指示を読む。既存 Issue・PR を確認し、同じ改善の重複作成や他の作業との競合を避ける。
- 実際のコード、呼び出し元、既存テストを読んで候補を評価する。差分の行数だけでなく、目的と影響範囲が狭く、変更理由を簡潔に説明できることを求める。
- 利用者から見える挙動を変えない。表示、API の結果、副作用、エラー時の挙動を含め、変更前後が同じと説明できるものに限定する。
- 変更の影響範囲を既存テストが十分にカバーしていることを必須とする。正常系・異常系・境界値や呼び出し元への影響など、候補に関連する観点を確認する。テストが通るだけでは網羅性の根拠にならない。
- 安全性の裏づけにテスト追加が必要な候補は見送る。確信が持てない候補、影響範囲を追い切れない候補も見送る。不具合ゼロを保証したとは表現しない。
- DB・認証・権限・外部サービス・デプロイ設定の変更は対象外。対象外の変更を必要とする候補も選ばない。
- 安全な候補が見つからなければ、確認した範囲と「該当なし」を報告し、実装用の Issue・PR は作らず終了する。件数を埋めるために変更を作らない。

### 依存関係の更新

直接依存のパッチ更新のみを候補に含める。宣言した依存の現行版と更新先が同じメジャー・マイナーバージョンであることを確認する。公式の変更履歴を調べ、利用箇所と既存テストから挙動の維持と安全性を説明できる更新に限る。

ロックファイルに現れる間接依存の変更も確認する。連鎖的に影響が広がる更新、互換性が不明な更新、既存テストで影響を確認できない更新は見送る。パッチ更新というだけで安全と判断しない。

## 専用ラベル

このスキルが作成する実装用 Issue・PR と、スキル自身の改善提案 Issue には、すべて `small-safe-improvements` ラベルを付ける。既存ラベルを確認し、存在しなければこの名前で作成する。他のラベルの変更や削除は行わない。作成後に付与を確認する。

## 実行

1. 選んだ1件について Issue を作成する。現状の問題、改善内容、対象範囲、既存テストによる安全性の根拠、検証予定を記載する。候補ごとの承認待ちは挟まず、PR 作成まで進める。
2. masusono-worktree スキルに従って専用 worktree を作成し、以降の編集・検証・コミット・push はそこで行う。メイン checkout や他の worktree の変更に触れない。
3. 選んだ改善だけを実装する。関連箇所の整理や追加の改善を同じ PR に混ぜない。
4. 変更範囲に必要な既存テストと静的解析、およびリポジトリで必須の検証を実行する。Docker Compose は worktree のラッパーを使う。変更前からある失敗が疑われる場合はベースでも確認する。
5. 検証失敗を今回の小さな変更の範囲で解消できなければ、変更範囲を広げず終了する。作成済み Issue に失敗内容・確認結果・残る作業を記録し、PR は作らない。検証を実行できず安全性の根拠が不足する場合も同様に扱う。
6. 検証が成功したら差分を確認し、対象ファイルだけをコミットする。リポジトリ指定の push スクリプトを使い、PR を作成する。PR に改善理由、安全性の根拠、実行した検証と結果、`Closes #<Issue番号>` を記載する。作成した PR をタスクに添付する。
7. 起動した開発サーバーはリポジトリの指示に従って停止する。worktree・ブランチ・ボリュームは自動削除しない。結果、Issue・PR のリンク、検証結果をユーザーに報告する。

## スキル自身の改善提案

作業後に、今回の実行からこのスキルの改善点が見つかった場合は、スキルを自動変更せず、別の Issue に提案を残す。実際に観察した問題、提案、理由を記載し、既存の提案と重複させない。改善点がなければ Issue は作らない。

この提案 Issue は通常の改善1件とは別枠で、実装・PR 作成の対象にはしない。スキルの対象範囲や安全基準を自己判断で緩めない。
