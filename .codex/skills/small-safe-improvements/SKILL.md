# Small Safe Improvements

このプロジェクトのコードを読み、小さく安全な改善を積み重ねる。1回の実行で扱う改善テーマは1件、対応する Issue と PR はそれぞれ1件とする。同じ目的・変更パターンの類似箇所は、ファイルが異なっても1件にまとめ、ファイル単位で別タスクに分けない。PR はマージせず、ユーザーが判断できる根拠を残す。

## 候補の選定

- リポジトリの AGENTS.md と、変更箇所に適用される指示を読む。既存 Issue・PR を確認し、同じ改善の重複作成や他の作業との競合を避ける。
- 候補選定前にベース参照を fetch する。指定がなければ `git fetch origin main` で `origin/main` を更新し、指定されたリモートブランチをベースにする場合はそのブランチを fetch する。メイン checkout のブランチ切り替えや pull は行わない。
- 候補の実装・呼び出し元・既存テストは、ローカル checkout の状態ではなく更新したベース参照で確認する。worktree 作成前は `git show origin/main:<path>` などを使い、ユーザー指定のベースがある場合はその参照を使う。
- 実際のコード、呼び出し元、既存テストを読んで候補を評価する。差分の行数だけでなく、目的と影響範囲が狭く、変更理由を簡潔に説明できることを求める。
- 利用者から見える挙動を変えない。表示、API の結果、副作用、エラー時の挙動を含め、変更前後が同じと説明できるものに限定する。
- 変更の影響範囲を既存テストが十分にカバーしていることを必須とする。正常系・異常系・境界値や呼び出し元への影響など、候補に関連する観点を確認する。テストが通るだけでは網羅性の根拠にならない。
- 安全性の裏づけにテスト追加が必要な候補は見送る。確信が持てない候補、影響範囲を追い切れない候補も見送る。不具合ゼロを保証したとは表現しない。
- DB・認証・権限・外部サービス・デプロイ設定の変更は対象外。対象外の変更を必要とする候補も選ばない。
- 安全な候補が見つからなければ、確認した範囲と「該当なし」を報告し、実装用の Issue・PR は作らず終了する。件数を埋めるために変更を作らない。

### 類似箇所の調査と集約

- 改修案を見つけたら、Issue 作成前に更新したベース参照のリポジトリ全体から類似箇所を探す。`git grep -n -e '<検索語>' <ベース参照> -- <対象パス>` などで同じ API・構文・処理パターンを検索し、表記違いも考慮して候補の実装・呼び出し元を読む。
- 同じ目的・変更パターンで対応できる箇所は、まとめて1つの Issue・PR の対象にする。文字列が似ているだけで挙動や変更理由が異なる箇所、別の改善テーマは混ぜない。
- 各箇所について、挙動の維持と既存テストのカバー範囲を確認する。集約後も目的と影響範囲が狭いことを求め、安全基準を満たさない箇所や既存 Issue・PR で対応中の箇所は除外し、その理由を残す。
- Issue・PR に、類似箇所を探した範囲、まとめて変更する箇所、除外した箇所があればその理由を記載する。類似箇所がなければ、その確認結果を記載する。

### 依存関係の更新

直接依存のパッチ更新のみを候補に含める。宣言した依存の現行版と更新先が同じメジャー・マイナーバージョンであることを確認する。公式の変更履歴を調べ、利用箇所と既存テストから挙動の維持と安全性を説明できる更新に限る。

ロックファイルに現れる間接依存の変更も確認する。連鎖的に影響が広がる更新、互換性が不明な更新、既存テストで影響を確認できない更新は見送る。パッチ更新というだけで安全と判断しない。

## 専用ラベル

このスキルが作成する実装用 Issue・PR と、スキル自身の改善提案 Issue には、すべて `small-safe-improvements` ラベルを付ける。既存ラベルを確認し、存在しなければこの名前で作成する。他のラベルの変更や削除は行わない。作成後に付与を確認する。

## 実行

1. Issue 作成直前にベース参照を再度 fetch し、集約した対象箇所がまだ未実装で、実装・呼び出し元・既存テストによる安全性の根拠が変わっていないことを確認する。一部が実装済み、または既存 Issue・PR と競合する場合は対象を再評価し、残る箇所で安全性と集約範囲を確認する。対象がなくなればその候補の Issue は作らず、別候補を評価する。選んだ1件について Issue を作成し、現状の問題、改善内容、対象範囲、既存テストによる安全性の根拠、検証予定を記載する。候補ごとの承認待ちは挟まず、PR 作成まで進める。
2. masusono-worktree スキルに従って専用 worktree を作成し、以降の編集・検証・コミット・push はそこで行う。メイン checkout や他の worktree の変更に触れない。
3. 選んだ改善テーマについて、候補選定で集約した類似箇所をまとめて実装する。実装中に同じパターンの未確認箇所が見つかった場合は、同じ安全基準で評価し、対象範囲と検証予定を Issue に反映する。別の目的の整理や追加の改善を同じ PR に混ぜない。
4. 下記の検証準備と実行順序に従い、変更範囲に必要な既存テストと静的解析、およびリポジトリで必須の検証を実行する。Docker Compose は worktree のラッパーを使う。変更前からある失敗が疑われる場合はベースでも確認する。
5. 検証失敗を今回の小さな変更の範囲で解消できなければ、変更範囲を広げず終了する。作成済み Issue に失敗内容・確認結果・残る作業を記録し、PR は作らない。検証を実行できず安全性の根拠が不足する場合も同様に扱う。
6. 検証が成功したら差分を確認し、対象ファイルだけをコミットする。リポジトリ指定の push スクリプトを使い、PR を作成する。PR に改善理由、安全性の根拠、実行した検証と結果、`Closes #<Issue番号>` を記載する。作成した PR をタスクに添付する。
7. PR 作成後は下記の「PR 作成後の CI 確認」に従い、作成した PR の最新コミットに対する CI 結果を確認する。ローカル検証の成功だけで完了扱いにしない。
8. 起動した開発サーバーはリポジトリの指示に従って停止する。worktree・ブランチ・ボリュームは自動削除しない。結果、Issue・PR のリンク、検証結果をユーザーに報告する。

### 検証準備と実行順序

- npm 依存は lockfile に従って `npm ci` で準備する。worktree のルートで、vite サービス起動前に `.codex/skills/masusono-worktree/scripts/compose.sh run --rm --no-deps vite npm ci --no-audit --no-fund` を実行し、成功を確認する。すでに vite が起動している場合は、この worktree の vite サービスを止めてから実行し、依存のインストールを重ねない。
- 新規の専用 `node_modules` ボリュームで `npm ci` が `EACCES` になった場合は、[masusono-worktree の権限エラー復旧手順](../masusono-worktree/SKILL.md#新規-node_modules-ボリュームの権限エラー)でマウントと所有者を確認し、対象 worktree に限定して復旧する。依存未準備のまま RSpec を開始しない。
- `compose.sh up --build -d` の終了だけで準備完了と判断しない。`compose.sh logs vite` で依存準備が正常に完了し、Vite が起動したことを確認してから RSpec を開始する。起動時にも npm install が実行されるため、`git diff -- backend/package.json backend/package-lock.json` で意図しない依存定義・lockfile の差分がないことを確認する。
- RSpec と Visual Regression（`scripts/push.sh` が実行する全画面比較を含む）は、同じ `backend/public/vite` にビルド出力を書き込むため並列実行しない。RSpec の終了と成功を確認してから Visual Regression または `scripts/push.sh` を開始する。絞り込んだテストで必須の全画面比較を代替しない。

### PR 作成後の CI 確認

- 作成した PR の先端コミットとチェック結果を確認し、対象の検証ジョブが完了して成功したことを確認する。古いコミットの成功や、待機中・実行中のチェックを成功として扱わない。スキップされたジョブは変更範囲や実行条件から理由を確認する。
- 複数件を続けて実行する場合は、作成した PR のリンクと先端コミットを記録し、他の作業を進める間も適切な間隔で CI 結果を追跡する。最終報告前に全 PR の最新結果を確認する。
- CI が失敗したら、失敗ジョブのログと artifact を調べる。画面比較では実画像・期待画像・差分画像を確認し、変更起因、環境起因、一時的な失敗を判断する。変更前からある失敗が疑われる場合は、必要に応じてベースでも確認する。
- 環境起因・一時的な失敗を示す根拠がある場合に限り、該当ジョブを1回再実行して結果を確認する。調査なしで再実行を繰り返したり、基準画像の更新や許容差の緩和だけで失敗を隠したりしない。再実行でも失敗した場合は再実行を続けず、原因を調べる。今回の小さな変更の範囲で解消できなければ、既存の Issue・PR に確認結果と残る作業を記録し、無関係な変更を加えず未完了として報告する。
- 最終報告にはローカル検証と CI 結果を分けて記載する。初回失敗と再実行結果があれば両方を報告し、再実行成功だけで根本原因が解消したと断定しない。未解消の失敗や、結果を確認できなかったチェックも明示する。

## スキル自身の改善提案

作業後に、今回の実行からこのスキルの改善点が見つかった場合は、スキルを自動変更せず、別の Issue に提案を残す。実際に観察した問題、提案、理由を記載し、既存の提案と重複させない。改善点がなければ Issue は作らない。

この提案 Issue は通常の改善1件とは別枠で、実装・PR 作成の対象にはしない。スキルの対象範囲や安全基準を自己判断で緩めない。
