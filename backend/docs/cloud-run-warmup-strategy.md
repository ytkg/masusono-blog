# Cloud Run ウォーム維持戦略（キャッシュ非採用）

- 最終更新: 2026-03-10
- 目的: Cloud Run のコールドスタートによる初回表示遅延を抑える

## 1. 背景

- これまでオリジン到達率削減を主目的としてキャッシュ戦略を検討していた
- 方針変更により、API/HTML のキャッシュ最適化は主戦略から外す
- 今後は Cloud Run インスタンスのウォーム維持（または定期起動）を主戦略とする

## 2. 決定事項

1. キャッシュ戦略は採用しない
2. `min instances = 1` は設定しない
3. 定期ヘルスチェックで Cloud Run へアクセスし、インスタンスを維持/起動する

## 3. 採用方針

- ウォームアップ対象: `GET /up`
- 実行方式: 外部スケジューラから定期実行（例: Cloud Scheduler）
- 期待効果:
  - 無通信時間が続く時間帯でも、次のユーザーアクセス時のコールドスタート確率を下げる
  - 常時起動よりコストを抑えながら遅延を緩和する

## 4. 運用ガイド（初期案）

- 実行間隔: 5〜10分（まずは 10 分で開始し、効果を見て短縮）
- タイムアウト: 10秒
- リクエスト先: 本番サービスの `/up`
- メソッド: `GET`
- リクエストヘッダ:
  - `Cache-Control: no-store`
  - `Pragma: no-cache`
- 判定:
  - 2xx を成功
  - 連続失敗時はアラート

## 5. 非目標（この戦略でやらないこと）

- API レスポンスの TTL 設計
- `ETag` / `If-None-Match` を使った再検証設計
- `s-maxage`, `stale-while-revalidate` を使った CDN キャッシュ最適化
- `min instances` での常時ウォーム維持

## 6. 監視項目

- Cloud Run のリクエスト数（スケジューラ経由分を区別して把握）
- 初回表示の応答時間（p95/p99）
- コールドスタート発生回数（確認可能な範囲でログ監視）
- ヘルスチェック失敗率

## 7. リスクと対策

- リスク: スケジューラ停止時にコールドスタートが再発
  - 対策: 失敗アラートと再実行手順を運用に含める
- リスク: 間隔が長すぎて効果が薄い
  - 対策: 間隔を段階的に調整し、レイテンシ実測で決定する
- リスク: 間隔が短すぎて不要コストが増える
  - 対策: 10分開始 -> 実測で最適化
